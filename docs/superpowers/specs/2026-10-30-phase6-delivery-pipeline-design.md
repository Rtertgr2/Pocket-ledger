# Phase 6 — Delivery Pipeline (Design)

Date: 2026-10-30
Status: code complete; the GitHub Actions run is blocked by an account-level restriction on
`Rtertgr2`, so releases are built locally and published to the app's own update feed (see
"Update feed" at the end of this document).
Scope: Phase 6 of the roadmap — repository, keystore, CI-built signed APK, in-app update check.
No store publishing, no OTA updates, no AAB/app-bundle path.

## Intent

Phases 1–5 produced an app that only exists on the machine that built it. Phase 6 makes the APK
something you can hand out: a tag on GitHub builds and signs the release, and the installed app can
tell you a newer build exists and open it.

## Deliverables

| Path | Purpose |
|---|---|
| `.github/workflows/build-apk.yml` | Tag (or manual dispatch) → checks → prebuild → signed release APK → GitHub Release |
| `plugins/withReleaseSigning.js` | Config plugin that adds the release signing config to the generated Gradle file |
| `scripts/stamp-version.mjs` | Writes the tag's version and a monotonic `versionCode` into `app.json` before prebuild |
| `src/services/updates/releases.ts` + `.test.ts` | GitHub Releases API check, version ordering, APK asset pick |
| `src/app/(tabs)/settings.tsx` | The real "ตรวจสอบอัปเดต" button replaces the previous placeholder |

## Decisions

### 1. Signing lives in a config plugin, not in `android/`

`android/` is generated by `expo prebuild` and gitignored, so a hand-edited `app/build.gradle`
signing config disappears on the next prebuild — and CI prebuilds from scratch every run.
`plugins/withReleaseSigning.js` (registered in `app.json`) inserts:

```gradle
signingConfigs {
    release {
        storeFile file(System.getenv("KEYSTORE_FILE") ?: "release.keystore")
        storePassword System.getenv("KEYSTORE_PASSWORD")
        keyAlias System.getenv("KEY_ALIAS")
        keyPassword System.getenv("KEY_PASSWORD")
    }
}
```

and switches only the `release` buildType to `signingConfig (System.getenv("KEYSTORE_FILE") ?
signingConfigs.release : signingConfigs.debug)`. Two consequences that matter:

- No secret is ever written into a file or the repository; Gradle reads the environment that CI
  fills from repository secrets.
- A local `assembleRelease` without those variables still works, signed with the debug key, so the
  plugin does not break day-to-day development.

The plugin throws a named error when the Expo template stops matching (missing `signingConfigs`,
`buildTypes`, or the debug signing line) instead of silently producing an unsigned APK.

### 2. The tag is the version

`scripts/stamp-version.mjs <version> <versionCode>` runs after checkout and before
`expo prebuild`, so the version baked into the APK is the tag without its `v`
(`v1.2.0` → `1.2.0`). `versionCode` comes from `github.run_number`, which is monotonic — Android
refuses to install an update whose `versionCode` is not higher, so deriving it from the version
string (e.g. `1.2.0` → `10200`) would break the first time a patch release was tagged out of order.

A manual dispatch stamps `<base>-dev.<run_number>`, which sorts *below* the release it was branched
from (`1.1.0-dev.7 < 1.1.0`), so a dev build never looks like an upgrade.

### 3. CI checks before it builds

The workflow runs `tsc --noEmit`, `npm test`, `npm run check` (schema + contrast) and
`expo lint` before Gradle. A red test therefore fails in two minutes, not after a fifteen-minute
Android build. `LANG/LC_ALL=C` is set at the job level because the Gradle zip-timestamp bug on a
Thai locale is not limited to this one machine.

### 4. The APK is verified, not assumed

After Gradle, the workflow runs `apksigner verify --print-certs` and fails when the certificate
looks like `CN=Android Debug` — the failure mode this whole plugin exists to prevent. The APK is
then renamed `pocket-ledger-<version>.apk`, checksummed into `SHA256SUMS.txt`, uploaded as a build
artifact, and attached to the GitHub Release with `--latest`.

`--latest` is not cosmetic: the in-app check reads `/releases/latest`, so a release left as a draft
or marked "not latest" would never reach an installed phone.

### 5. The update check is one GET with a verdict, and installs nothing

`checkForUpdate({ currentVersion })` calls
`https://api.github.com/repos/Rtertgr2/Pocket-ledger/releases/latest`, validates the body once in
`parseRelease`, and returns `{ currentVersion, latest, available }`. The screen turns that into one
dialog: the release notes and a **ดาวน์โหลด APK** button that opens the browser on the APK asset
(or the release page when a release carries no asset). Nothing is downloaded, staged or installed by
the app, so the ledger cannot be touched by a failed check.

The module deliberately does not import `expo-constants`: the installed version is passed in from
the screen, which keeps the ordering rules testable with plain `node --test`.

Version ordering is numeric per segment, prerelease below its release:

```
compareVersions('1.9.9', '1.10.0')      → -1     (lexical comparison would get this wrong)
compareVersions('1.1.0-dev.3', '1.1.0') → -1
compareVersions('v1.0.0', '1.0.0')      →  0
```

Failures are Thai toasts phrased for the settings screen: no release yet (404), rate limited (403),
other status, unreadable body, timeout, and connection failure.

### 6. Keystore handling

The keystore was generated with `keytool` (RSA 2048, 10 000 days, alias `pocketledger`) and stored
outside the repository in `~/.pocket-ledger/` next to its password file (`chmod 600`). Only the
base64 of the keystore and the passwords were pushed to repository secrets:

`ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`.

The keystore is the app's signing identity: lose it and an installed copy can no longer be updated
in place. `~/.pocket-ledger/` must be backed up somewhere that is not this laptop.

## Blocked: GitHub Actions is disabled for this account

`gh workflow run build-apk.yml` fails with:

```
HTTP 422: Actions has been disabled for this user.
```

Repo-level Actions permissions are `{ "enabled": true, "allowed_actions": "all" }`, so the block is
on the account, not the repository. Unauthenticated requests confirm the account is not visible at
all:

```
GET https://api.github.com/users/Rtertgr2        → 404
GET https://api.github.com/repos/Rtertgr2/Pocket-ledger        → 404   (API says PUBLIC)
GET https://github.com/Rtertgr2/Pocket-ledger    → 404
```

Authenticated requests succeed (admin/push on the repo), so this is GitHub restricting the account
(typically a spam flag on a young account), not a misconfiguration on our side.

Consequences until GitHub lifts it:

1. No workflow run, so no CI-built APK. The workflow is committed and ready.
2. Anonymous API 404 means the in-app check on a phone cannot see the repository either — it will
   report "ยังไม่มีการเผยแพร่เวอร์ชันบน GitHub" no matter what is published. Verified against the
   published v1.0.0: the service returned that message for both `0.9.0` and `1.0.0`.
3. Release downloads are not reachable publicly either:
   `curl -L .../releases/download/v1.0.0/pocket-ledger-1.0.0.apk` → `404` (the same URL works for
   the repository owner while signed in).

Nothing in the code should be changed to work around this: a private token inside the app would leak
it, and pointing the checker at a mirror would hide the real state.

## Update feed — the channel that actually works (2026-10-30, same day)

On the phone, the GitHub check showed "ยังไม่มีการเผยแพร่เวอร์ชันบน GitHub" even though `v1.0.0` was
published. Re-checked from outside the account:

```
GET /repos/Rtertgr2/Pocket-ledger/releases/latest  (anonymous) → 404
GET /repos/Rtertgr2/Pocket-ledger                   (anonymous) → 404
GET …/releases/latest                              (with token) → 200, v1.0.0, 2 assets
```

So the app was right and GitHub simply hides the account. No client-side change could fix that:
an app that shipped a token would leak it, and any GitHub URL under a hidden account 404s for every
phone. The channel was replaced instead of patched.

### Design

A Worker + R2 bucket on Freebuff Sites, in `update-feed/`:

| Route | Behaviour |
|---|---|
| `GET /latest.json` | the manifest the app reads, `cache-control: no-store` |
| `GET /<file>` | streams the object from R2 with its stored content type |
| `PUT /admin/<file>` | the only write path; requires `Authorization: Bearer $UPLOAD_TOKEN` |

Manifest shape (validated by `parseFeed` in one place):

```json
{
  "format": "pocket-ledger.update",
  "version": "1.0.1",
  "notes": "…",
  "apkUrl": "https://<site>/pocket-ledger-1.0.1.apk",
  "publishedAt": "2026-10-30T10:29:47.729Z"
}
```

Decisions worth keeping:

- **The APK lives in the same place as the manifest.** Two hosts would mean two things to keep in
  sync and two ways for a release to half-publish.
- **Uploads are a separate, token-guarded route.** Downloads stay anonymous and cacheable; only the
  person holding `.secrets/upload-token.txt` can replace a file. The token is a Worker secret, and
  the file is gitignored.
- **Order matters in the publisher.** `scripts/publish-feed.mjs` uploads the APK first and
  `latest.json` last, so the feed never advertises a version whose file is not there yet.
- **Cache-busting on the client.** The manifest is served `no-store` and the app appends `?t=<ms>`,
  because a cached manifest is a missed update.
- **60MB upload cap.** The Worker rejects larger bodies, which matches the arm64-only APK (31MB) and
  keeps a stray universal 95MB APK from being published.
- **`format` is checked** when present, so a JSON file from somewhere else is rejected rather than
  read as a version.

### What changed in the app

- `src/services/updates/releases.ts` (GitHub) was replaced by `src/services/updates/feed.ts`, which
  keeps the version ordering and the Thai error phrasing but reads the manifest. Tests moved with it.
- `app.json` is now `1.0.1` / `versionCode 2`, so the feed's release installs over an existing 1.0.0.
- `update-feed/README.md` documents publishing and token rotation.

### Consequences

- The first install of a build with the new checker still has to be manual: a phone on 1.0.0 runs the
  old GitHub check and cannot discover 1.0.1. From 1.0.1 onward the button works.
- The feed is now a second thing to keep alive. If the site is deleted or unpublished, the button
  fails with a network-style message and nothing else in the app is affected.
- `build-apk.yml` still uploads to GitHub Releases when Actions is restored; the feed step is not in
  that workflow, so a restored CI would still need `publish-feed.mjs` run once per release.

## Out of scope

- Play Store / AAB publishing.
- Over-the-air (EAS Update) JavaScript updates.
- Per-ABI APK splits — the current release APK carries every ABI and is ~95 MB.
- Automatic background update checks; the check is a button.
- Signing-key rotation or `apksigner` lineage.
